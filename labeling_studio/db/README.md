# db/ — 원본 데이터셋을 두는 곳

여기에 데이터셋 폴더를 통째로 넣으면 스튜디오가 알아서 찾는다.
**이 폴더의 내용은 git 에 올라가지 않는다**(`.gitignore`). 데이터는 각자 로컬에 둔다.

```
db/
└── <데이터셋 이름>/
    ├── data.yaml            nc / names
    ├── train/
    │   ├── images/
    │   └── labels/          YOLO txt (없어도 된다 — 그게 이 도구의 출발점이다)
    ├── valid/               val · valid 아무 이름이나 된다
    └── test/
```

스플릿 폴더명은 하드코딩돼 있지 않다. **`images/` 와 `labels/` 가 형제로 있는
디렉터리**를 찾아 들어가므로 `val` 이든 `valid` 든 상관없고, 스플릿이 없는 단일
폴더도 인식한다.

## 새 데이터셋을 받으면 0번 작업

```bash
python dedup_dataset.py <데이터셋> --dry-run --preview 8
```

**스플릿 사이에 같은 사진이 섞여 있는지부터 본다.** 채점표에 답이 적혀 있는 것과
같기 때문이다. 개발에 쓴 데이터셋에서는 valid 의 12.0%, test 의 10.9% 가 train 에
같은 사진을 갖고 있었다.

그런데 **파일 해시로는 안 잡힌다** — 배포 전에 전량 재인코딩되어 바이트가 같은
파일이 한 장도 없었다. 파일명도 연번이라 중복이 없다. 그림을 봐야만 잡힌다.
웹에서 긁어 모은 데이터셋은 이 문제를 거의 항상 갖고 있다.

납득되면 `--dry-run` 을 빼고 다시 실행한다. 남기는 우선순위는 **train > valid > test**
로, 사람이 라벨할 자원인 train 은 한 장도 잃지 않고 평가셋 쪽을 깎는다.

## 원본은 봉인한다

이 도구는 `db/` 를 **읽기만** 한다. 편집 결과는 전부 `work/<작업공간>/` 으로 간다.
작업공간이 없으면 편집 자체가 잠긴다.

라벨 파일에 OS 읽기 전용 속성까지 걸어 두면 다른 도구로도 못 건드린다.
정답지가 조용히 바뀌면 그때까지의 측정이 전부 무의미해지므로, 봉인은 논리적
수준이 아니라 물리적 수준에 두는 편이 낫다.

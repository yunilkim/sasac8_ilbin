# 연속형 라벨링 (Human-in-the-loop) 구현 계획

작성 2026-08-18 · 근거 실측은 `tools/bench_train_time.py`, 시나리오는 `tools/sim_continuous.py`

---

## 1. 무엇을 만드는가

사람이 라벨링하는 동안 GPU 가 뒤에서 학습하고, 새 모델이 나오면 아직 안 연 이미지를
다시 예측해 둔다. 사람은 학습을 기다리지 않는다.

```
        사람 라벨링 ──┐
                      ├─→ 확정 라벨 ──→ 백그라운드 학습 ──→ 새 모델
        사람 라벨링 ←─┘                                        │
              ↑                                                │
              └──────── 미개봉 이미지 재예측 (37초) ←───────────┘
```

기존 방식은 사람과 GPU 가 서로 기다렸다(50장 → 학습 → 대기 → 확인 → 다음 50장).
바꾸면 둘이 동시에 돈다.

## 2. 목표 지표는 대기시간이 아니다

**사람의 대기시간은 이미 0 이고 앞으로도 0 이다.** 예측은 176 img/s 라 6,681장 전량을
37초에 다시 만든다. 큐가 빌 일이 없으므로 Prediction Queue 를 미리 채워둘 필요조차 없다.

느린 것은 학습뿐이다. 그래서 진짜 비용은 **낡음(staleness)** 이다 --
지금 보고 있는 예측을 만든 모델이 몇 장 뒤처져 있는가.

| 지표 | 뜻 | 어디서 나오나 |
|---|---|---|
| 낡음 | 사람 진도 − 현재 모델의 학습분 | 새로 기록해야 함 |
| Acceptance / Modification / Rejection | 승인 / 수정 / 삭제 비율 | **이미 있음** — `meta` 의 `ops.kept/adjusted/deleted` |
| Human Time / Image | 장당 실측 초 | **이미 있음** — `ops.seconds` |
| Time-to-Autonomy | 몇 장에서 승인률 N% 를 넘나 | 위 둘의 시간축 집계 |

## 3. 이미 구현돼 있는 것 (다시 만들지 말 것)

`work/<작업공간>/meta/<split>/<이미지>.json` 이 이미 이렇게 생겼다:

```json
{"image":"...", "src":["A","A","C"], "conf":[...], "tier":[...],
 "ops":{"drawn":3,"deleted":0,"adjusted":0,"kept":0,"seconds":15.56},
 "cost_sec":15.0, "manual_sec":15.0, "promoted":0, "ts":"..."}
```

- 박스별 출처 A/B/C/D, 이미지별 실측 초, 편집 연산 내역이 전부 들어 있다.
- 순환 오염 방지도 이미 있다 — `train_model.py` 는 **meta 기록이 있는 이미지만** 학습에
  쓴다. 예측만 있고 사람이 안 본 이미지는 원천적으로 안 들어간다.

**8단계 상태머신(RAW→…→FINAL)은 만들지 않는다.** 지금은 "meta 기록이 있으면 사람이
확정한 것"이라는 규칙 하나가 같은 일을 한다. 상태가 8개면 불일치 조합을 처리하는 코드가
상태 수의 제곱으로 는다. 필요한 것은 두 가지뿐 — **사람이 봤나 / 어느 모델이 예측했나.**

빠진 것은 하나다: **`pred_model` 이 레코드에 없다.** 지금은 모델이 작업공간 단위
(`workspace.json` 의 `model`)라 이미지마다 다를 수 없다. 연속형에서는 작업 중에 모델이
바뀌므로 이것이 레코드로 내려와야 한다.

## 4. 학습을 3배 빠르게 (실측 근거)

`tools/bench_train_time.py` 참조. 요약:

- **학습 에폭의 80% 가 검증이다.** valid 1258장을 매 에폭 다시 재기 때문. 학습 계산은
  에폭당 0.66초 + 장당 5.6ms 라, 150장을 500장으로 늘려도 2초 느는 게 전부다.
- **GPU 쪽은 손댈 게 없다.** batch·half·conf·max_det 어느 것도 1초를 못 줄인다.
  batch=128 은 오히려 4.6배 느려진다.
- **윈도우 워커 spawn 이 워커당 +2초.** standalone `val()` 은 `workers=0` 이 3배 빠르다.
  학습 루프는 로더를 재사용하므로 해당 없고, `train_model.py:588` 은 이미 `workers=0`.

**확인 완료 (2026-08-18).** 학습분 150장·seed 0 을 조건만 바꿔 80에폭 완주시키고,
나온 `best.pt` 를 valid 전량(1258장)으로 다시 재서 비교했다.

| 설정 | 학습 시간 | mAP50 | mAP50-95 |
|---|---|---|---|
| 기준 (검증 1258장 · 매 에폭) | 10.2분 | 0.8132 | 0.5213 |
| 검증 1258장 · 5에폭마다 | 4.2분 | 0.8124 | 0.5213 |
| 검증 400장 · 매 에폭 | 5.1분 | 0.8124 | 0.5213 |
| **검증 400장 · 5에폭마다** | **3.0분** | **0.8124** | **0.5213** |

**3.4배 빨라지고 손해는 mAP50 0.0008** — 잡음(0.002) 이하이고 mAP50-95 는 소수점
4자리까지 같다.

**손해의 원인은 둘로 나눌 수 없다.** 검증셋만 줄여도, 주기만 늘려도, 둘 다 해도
전부 똑같이 0.8124 다. 기준만 `epoch 79` 를 골랐고 나머지 셋은 `epoch 80` 을 골랐기
때문이다(후반 곡선이 평평해 79 와 80 이 사실상 같다). 즉 0.0008 은 어느 설정을
바꿨느냐와 무관하게 **best 에폭 선택이 한 칸 옮겨간 값**이다.
※ 처음에 두 조건만 보고 "주기 늘리기는 공짜"라고 적었으나 세 번째 조건이 이를 뒤집었다.

구조는 이미 맞다. `train_model.py` 가 학습 후 `best.pt` 를 **전량으로 다시 검증**해
`model.json` 에 적는다. 학습 중 감시는 400장으로 싸게, 보고 숫자는 1258장으로 정확하게.

## 5. 시나리오 (제로샷 50장으로 시작)

`tools/sim_continuous.py` 출력. 학습시간 `143 + 0.385n` 초 기준.

| 시각 | 모델 | 학습분 | 사람 진도 | 낡음 | 초/장 |
|---|---|---|---|---|---|
| 0분 | 제로샷 | — | 0장 | — | 9.7초 |
| 10.8분 | v1 | 50장 | 66장 | 16장 | 7.1초 |
| 16.5분 | v3 | 91장 | 117장 | 26장 | 6.1초 |
| 23.0분 | v5 | 148장 | 184장 | 36장 | 4.7초 |
| 30.4분 | v7 | 230장 | 282장 | 52장 | 4.0초 |
| 39.2분 | v9 | 345장 | 421장 | 76장 | 3.3초 |

| 목표 | 소요 | 모델 갱신 | 빈 화면이면 | 절감 |
|---|---|---|---|---|
| 500장 | 44분 | 9번 | 1.8시간 | 60% |
| 1,000장 | 1.1시간 | 13번 | 3.6시간 | 70% |
| **6,681장 (train 전량)** | **4.1시간** | 22번 | 23.9시간 | **83%** |

가장 비싼 구간은 **처음 10.8분** — 제로샷만 있는 상태로 66장.

이것이 프로젝트의 모양을 바꾼다. 원래 질문은 "사람 라벨 몇 장이면 되나"(답 150장)였는데,
연속형에서는 **"전부 해도 4시간"** 이 된다. GT 가 없는 새 도메인에서는 어차피 전량 라벨이
필요하므로 이쪽이 실제 쓰임에 맞다.

**약한 곳:** 곡선의 50·300장 지점은 실측이 아니라 보간이다. 44분이라는 숫자가 여기 걸려
있다. `y11s_n50_random` 이 이미 있으니 예측 만들어 GT 로 재면 확정된다.
그리고 12.9초/장은 26장 몰아치기 값이라 4시간 연속이면 사람이 느려진다 — 낙관치다.

## 6. 앵커링 — 정책과 안전장치

**정책 (사장님 결정, 2026-08-18):** 앵커링은 받아들인다. 인간과 모델의 협업이 목표이므로
모델이 그린 것을 사람이 승인하는 것은 결함이 아니라 제품이 작동하는 모습이다.

**예외:** 채점용 답지(valid/test)는 빈 화면에서 만든다. 모델이 도운 답지로 그 모델을
채점하면 점수가 올랐을 때 모델이 좋아진 건지 답지가 모델을 닮은 건지 구분할 수 없다.

**안전장치 — 블라인드 프로브 (미결정):** 후반에 사람은 1.9초/장까지 간다. 사실상 "다음"을
누르는 속도이고, 그 라벨이 곧 데이터셋이 된다. 연속형에서는 v3 가 v2 가 앵커링한 라벨로
학습되므로 편향이 자기확인 루프를 돈다. 그런데 **Acceptance Rate 는 그 루프가 최대화하는
바로 그 지표라 단독으로는 품질 지표가 될 수 없다** (승인률↑, 장당시간↓, 품질은 정체).

대책: 큐의 5% 를 예고 없이 빈 화면으로 내보내고 시드 받은 것과 비교한다. 비용은 전체의
5%(4.1시간 → 4.4시간). 막는 것이 아니라 **얼마나 되는지 보이게만** 하는 것이라 정책과
충돌하지 않는다. `work/anchor_1_blank` / `anchor_2_seeded` 의 일회성 측정을 상시 계기로
바꾸는 셈이다.

### 실행 방법 (현재)

```
1. "학습 워커 실행.bat"   — 창을 열어둔 채로 둔다
2. 스튜디오를 열고 라벨링한다
```

작업공간의 `workspace.json` 에 `live` 를 넣으면 켜진다:

```json
"live": {"enabled": true, "every": 50, "dataset": "vest-helmet_crop_dedup",
         "split": "train", "epochs": 80, "val_fast_n": 400, "val_period": 5}
```

### 검증한 것 (2026-08-18 실측)

- 큐 규약 — 요청 3개가 쌓이면 **가장 최근 것만 실행**하고 나머지는 `superseded` 로 넘어간다.
  `os.rename` 원자성으로 워커가 둘이어도 중복 실행이 없다. 워커가 죽으면 `running` 에
  남은 것을 기동 시 큐로 되돌린다.
- 전 구간 한 바퀴 — 요청 → 학습 → `make_preds` → `done` → 스튜디오가 주워 `pred_dir` 교체.
  예측 6,655개 = 6,681장 − 학습에 쓴 26장. **학습 이미지 제외가 실제로 동작한다.**
- 낡음 계산 — 확정 46장 · 모델 학습분 26장 → 낡음 20장.

### 설계 제약 두 가지 (2번 워커)

- **반드시 별도 프로세스.** 스레드로 하면 Tkinter 가 GIL 을 잡고 있어 UI 가 얼어붙는다.
- **통신은 소켓이 아니라 파일로.** `work/<작업공간>/jobs/` 에 요청을 떨어뜨리면 워커가
  집어가고, 끝나면 `models/` 에 쓰고 완료 표시를 남긴다. 스튜디오는 폴더만 본다.
  기존 3구역 규약과 같은 방식이라 새 개념이 안 는다.
